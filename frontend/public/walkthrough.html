Why an expense tracker In my own words

I didn’t start this course with a product I wanted to build. What I wanted was to learn the whole process properly: writing specs, testing, CI, deploying, and fixing things when they break. So I picked a simple, familiar problem on purpose. With an idea I already understood, I could spend my effort on doing each step carefully instead of working out what the app should be.

The app is small, but getting the details right wasn’t. Money had to be stored exactly, dates had to follow Indian time, limits had to behave sensibly at the edges, and the online version had to stay honest about what it can’t do. Building it taught me much more than I expected, and I now understand how each part fits together, from the spec to the live site.

The big picture

What the app does, in one sentence, and the four places it lives.

The app lets a person record everyday expenses by category, set a monthly limit for each category, and see whether they are staying within it goal-spec. Each person has their own account (a username and password), and after logging in sees and changes only their own data goal-spec. It looks like one web page, but behind it are separate pieces that run in different places on the internet.

The basic idea behind almost every website: the part you see is the frontend, and it runs inside your browser. The part that checks rules and keeps data is the backend, a program running on a server. The backend stores everything in a database. They talk by sending requests and responses over the internet.

Press Play a request to watch how one visit travels between the parts, or Play a code change to see how new code goes live.

In words

  1. Getting the page. When you open the link, your browser downloads the page's files from GitHub Pages. From then on, the page runs inside your browser.
  2. Asking for data. The page sends requests to the backend on Render, using the API: an agreed list of endpoints such as /api/expenses, with data written as JSON.
  3. Reading and saving. The backend checks the request against the rules, then asks the PostgreSQL database on Neon for data, or saves to it, using SQL.
  4. The answer comes back the same way: database → backend → page, which then updates what you see.
  5. Changing the code. Separately, every time code is pushed to the GitHub repository, GitHub Actions runs every automated test and deploys the new page only if they all pass. The backend is different: it currently needs a manual deploy on Render, because Render's auto-deploy didn't trigger (see Render's gotchas).

GitHub Pages: the page you see

What it does

GitHub Pages is GitHub's free hosting for static websites. It hands out the files that make up the page (HTML for the structure, CSS for the look, JavaScript for the behaviour) at shivanisujith.github.io/expense-tracker. It runs no code of its own: once your browser has the files, all the work happens in your browser.

The page is written with React and turned into those files by Vite during the build. In your browser it draws the dashboard, runs the convenience checks on what you type, sends requests to the backend, and shows the answers.

Why it's needed

Your browser has to download the page from somewhere public. The goal spec chose GitHub Pages for the frontend goal-spec. Free, and it lives right next to the code My inference.

Design decisions

  • The page never adds up money. Every total, "spent" and "remaining" comes from the backend; the page only formats it frontend-spec. One place does the maths, so the cards, the total and the insight line can never disagree.
  • Checks on the page are for convenience only. The page catches mistakes early (empty amount, date in the future) so you get a quick message, but the backend checks everything again goal-spec, Constraints.
  • Money is never a decimal number. When you type 12.50, money.js splits the text at the dot and builds 1250 paise with whole numbers. It never multiplies a decimal by 100 code comment in money.js, which avoids floating-point rounding errors.
  • The backend's address is a build setting called VITE_API_BASE. GitHub Actions fills it in with the Render address when it builds the online page; without it the laptop address http://localhost:8000/api is used frontend-spec, api.js.
  • The "base path". GitHub Pages serves this project under /expense-tracker/, so the build tells Vite to put every file there. The laptop version uses / vite.config.js.
  • A 90-second wait, and a calm "waking up" note. See Journey 2 below api-contract-spec.
  • Colours with a readability rule. Pink, cream, plum and sage, where every text colour meets the WCAG AA contrast standard, and red is used only for over-limit warnings and errors, so red always means "something's wrong" frontend-spec.
  • The log in screen comes first. With no saved token, the page shows the log in screen instead of the dashboard. "Create an account" adds a short warning in normal text, not red, because it isn't an error: "This is a demo. Don't use a password you use anywhere else." frontend-spec.
  • Popups use the browser's built-in <dialog>, which handles blocking the page behind and the Escape key AddExpenseModal.jsx comment. Clicking outside a popup does not close it, so typed details aren't lost by accident frontend-spec.

What else could have been used

  • Other static hosts such as Netlify, Vercel or Cloudflare Pages: they would work about the same My inference.
  • Serving the page from the same Render server as the backend. Then page and backend would share one address, so CORS wouldn't be needed, but every page visit would also have to wake the sleeping server My inference.
  • Plain HTML and JavaScript without React. Fine for a tiny page, but harder to keep tidy with popups, loading states and many boxes updating together My inference.

Gotchas

  • The backend address is baked in when the page is built. If the Render address ever changed, the page would have to be rebuilt. The deploy job stops with a clear error if VITE_API_BASE isn't set ci.yml.
  • Everything in the page is public. Anyone can read the page's code in their browser, so it must never contain a password. The backend address is not a secret frontend-spec.
  • The login token is kept in localStorage. That way a reload stays logged in, but a harmful script on the page could read it, and that storage is shared by every page under https://shivanisujith.github.io. Fine for learning, not for real use goal-spec, Known Limitations.
  • Wrong base path = blank page. If the base path were wrong, the browser would look for the files in the wrong folder and the page would load blank My inference.
  • Two clocks. The date under the title and the "current month" come from your computer's clock (in IST), while the category cards' month comes from the backend. If your computer's clock is wrong they could disagree. The spec accepts this; the backend still refuses future months frontend-spec.
  • Files in frontend/public/ are copied as they are. That's how this walkthrough page gets published too: Vite copies it into the build without changing it My inference, from how Vite treats that folder.

Interview questions

Why does the page turn "12.50" into 1250 by handling text, instead of just multiplying by 100?Show answer
Computers store most decimal numbers approximately (floating point). For example, in JavaScript 0.1 + 0.2 gives 0.30000000000000004. Multiplying a decimal rupee amount by 100 can leave tiny errors like that, and money totals would then drift. So the page reads the rupees and the paise as two whole numbers and combines them, and everything after that is whole paise. The backend also stores whole paise, so totals are always exact (goal-spec, Constraints).
The page already refuses an amount of 0. Why does the backend check it again?Show answer
Because the page isn't the only way in. Anyone can send requests straight to the backend (with a tool like curl, or from the browser's developer tools), skipping the page completely. Logging in doesn't change this: a logged-in person can send any values they like with their own token. So the rule is enforced where the data is saved. The page's check only exists to give a quick, friendly message. Acceptance criterion 4 even tests that the backend refuses a bad category "even if the frontend sends it".
Why is the build's base path /expense-tracker/, but / when running on the laptop?Show answer
GitHub Pages serves a project's site in a folder named after the repository: shivanisujith.github.io/expense-tracker/. The page's files must say they live there, or the browser will look for them at the top of the site and find nothing. On the laptop, npm run dev serves the page at the top level (localhost:5173/), so it uses /. vite.config.js picks the right one depending on whether it is building or running the dev server.

Render: the backend

What it does

Render is a hosting company that runs programs on its servers. Here it runs the backend: a Python program built with FastAPI (the code is in backend/app/). For every request it:

  1. checks that the page asking is allowed (CORS),
  2. checks who is logged in, from the token sent with the request (Journey 3), and refuses with 401 if nobody is,
  3. checks the input against the rules (validation, in validation.py),
  4. reads or writes the database,
  5. adds up totals, works out who is over their limit and builds the "insight" line,
  6. answers in JSON with a status code: 200/201 if it worked, 401 if you're not logged in, 422 if the input broke a rule, 404 if the thing doesn't exist (or belongs to another account), 500 if something broke.

There are 15 endpoints, all listed in specs/api-contract-spec.md, for example POST /api/expenses (add), GET /api/summary (this month's cards), GET /api/months/2026-09/total and POST /api/auth/signup (create an account).

Why it's needed

  • The data has to be shared and kept somewhere other than your browser, so it survives reloads and works from any device goal-spec, criterion 1.
  • The rules must be enforced somewhere the user can't skip goal-spec, Constraints.
  • The database password must stay secret. A program on a server can hold it; a page in your browser can't backend-spec, Settings.

Design decisions

  • React frontend, FastAPI backend was the chosen stack goal-spec. It was weighed against a plain spreadsheet and rejected, because a spreadsheet can't refuse a negative amount or warn about a limit, and the course is about building and testing a real web app goal-spec.
  • One error shape for everything: {"error": {"code", "message", "field"}}. The message is plain English, safe to show as it is, and field tells the page which box to put it under api-contract-spec.
  • Fixed checking order. If several fields are wrong, only the first one is reported (amount, then category, then date, then note), so the same bad input always gives the same answer api-contract-spec.
  • "Today" is always worked out in India time (clock.py), even though Render's server clock runs on UTC backend-spec.
  • Crashes still carry CORS headers. The part that turns unexpected crashes into a 500 answer is placed inside the CORS part, "so the browser can tell 'server error' from 'can't reach server'" code comment in main.py.
  • Same code for two databases. A small wrapper in db.py lets the rest of the backend talk to SQLite (laptop) or PostgreSQL (online) the same way. The DATABASE_URL environment variable decides which backend-spec, db.py.
  • An upper limit of Rs 10,00,00,000.00 on any amount or limit, added after huge numbers were found to break the totals commit 2d71ab5.
  • Passwords are never stored. Only an Argon2 password hash is saved, made by the argon2-cffi library, "the current recommended way to store passwords" goal-spec. Tokens aren't stored either, only their SHA-256 fingerprint, "so someone who copies the database file can't use it to log in" backend-spec.
  • Someone else's id looks exactly like a missing one. Editing another account's expense gives the same 404 as an id that doesn't exist, "so guessing ids reveals nothing" backend-spec, rule O2.
  • Requests must say they are JSON (the Content-Type: application/json label), otherwise they are refused api-contract-spec.

What else could have been used

  • Other Python frameworks (Flask, Django) or a JavaScript backend (Node with Express) would all work. FastAPI gives automatic request reading and a built-in documentation page at /docs My inference.
  • Other hosts (Fly.io, Railway, a rented server), or a paid Render plan that doesn't sleep. The goal spec says it would move to paid plans "if the app needs real personal data or more than a course demo's traffic", and that "login here is a demo and stays on the free plans" goal-spec.

Gotchas

  • The free server sleeps. After 15 minutes with no visitors it sleeps, and the next visit waits about a minute while it wakes goal-spec.
  • Its disk is wiped on every restart and redeploy, which is why the data can't live in a SQLite file on Render goal-spec.
  • CORS is not security. It only stops other web pages from reading the answers in a browser. Anyone can still call the API directly api-contract-spec.
  • Automatic deploys didn't happen. A comment in ci.yml says "Render deploys the backend only after these checks pass", but in practice Render's auto-deploy never triggered: the backend only updated after a manual deploy from Render's dashboard Recorded: build sessions. So after pushing backend changes, someone has to remember to deploy them, and the live page and the live backend can briefly be out of step. Before the login deploy, auto-deploy was switched off on purpose, so the backend only updates when deployed by hand once CI is green Recorded: build sessions.
  • Render's own settings aren't in the repo. The start command, the secret DATABASE_URL and ALLOWED_ORIGINS live in Render's dashboard, so they can't be reviewed from the code My inference.
  • Hashing passwords is slow on purpose. Argon2 is designed to take real time and memory, so guessing passwords is expensive. On the free server's small CPU, signing up or logging in can take a second or two longer than other requests My inference.
  • Check, then act. Some rules are checked and then acted on as two separate steps (for example "fewer than 20 categories?" then "add one"). If two people did this at the exact same moment, both could pass the check. Not tested, and unlikely for a demo My inference, from reading main.py.

Interview questions

Why does the backend work out "today" in India time instead of just using the server's clock?Show answer
Render's server runs on UTC, which is 5½ hours behind India. Between midnight and 5:30 am in India, the server would still think it was yesterday, so an expense dated "today" would be refused as a future date. clock.py asks for the date in the Asia/Kolkata time zone instead. A bonus: the tests swap that one function for a fixed date (7 October 2026), so date rules can be tested reliably.
Someone sends an expense with category "food", but the category is called "Food". What happens, and why?Show answer
It is refused with a 422 invalid_category error, and nothing is saved. Expense categories must match a current name exactly, capitals included (backend rule 2), so a typo or a deleted category can never slip in. Category names are compared ignoring capitals for a different reason: so you can't create both "Food" and "food" (rule 14).
Why does it matter that a 500 "server error" still carries CORS headers?Show answer
If an answer comes back without the CORS permission headers, the browser hides it from the page entirely, and to the page that looks just like the server not answering at all. The user would see "Can't reach the server" when the real problem was a crash. By placing the crash handler inside the CORS layer, even a 500 gets the headers, so the page can show the correct message: "Something went wrong on the server."

Neon: the database

What it does

Neon hosts a PostgreSQL database that holds all the online data in five tables:

TableOne row per…Columns
usersaccountid, username, password_hash, created_at
sessionslogged-in sessionid, user_id, token_hash, created_at, expires_at
categoriescategoryid, user_id, name, icon
expensesexpenseid, amount_paise, category_id, date, note, created_at
category_limitscategory with a limitcategory_id, limit_paise

Expenses and limits have no user_id of their own: they belong to whoever owns their category, "so ownership is written down in only one place and can't disagree" backend-spec. On the laptop the same tables live in a SQLite file instead, backend/expenses-login.db for the login version, with the same rules backend-spec.

Why it's needed

The data must survive restarts and redeploys. Render's free disk is wiped every time, so a SQLite file there would lose everything. Render's own free PostgreSQL was rejected because it is deleted 30 days after it's created goal-spec.

Design decisions

  • Money as whole paise in big whole-number columns (BIGINT), never decimals goal-spec, backend-spec.
  • Expenses point to their category by id, not by name. Renaming "Food" to "Groceries" changes one row in categories, and every expense follows automatically backend-spec. Ids are never reused, even after deletion backend-spec.
  • The database has its own safety net. CHECK rules (amount > 0, name 1–30 characters), references (an expense must point at a real category), and a unique index on the lower-case name within each account. The code comment says these are "a last safety net; validation.py gives the real errors" db.py.
  • Set up once, then left alone. When the backend starts and the database is empty, it creates the tables in one all-or-nothing transaction; each new account gets its six starting categories when it signs up. If the tables are current, it changes nothing, so restarts keep the data backend-spec.
  • Upgraded in place for accounts. The online database already had expenses before login existed. When the login backend first starts, it adds the users and sessions tables and the new category columns in one transaction, counts the categories, expenses and limits before and after, and undoes everything if they differ. The old data is kept "unclaimed" until the first sign-up, which takes all of it backend-spec, "Upgrading the online database to accounts". The backend can't copy an online database, so the backup is made by hand in the Neon dashboard before deploying goal-spec, criterion 34.
  • Sums are forced to whole numbers. Every SUM is wrapped in CAST(… AS BIGINT) and there's a test called "sums are whole numbers, not decimals" commit c8003b1, test_database.py. Why: PostgreSQL returns the sum of big whole numbers as a decimal type, which would reach the page as 1250.0-style values My inference, from how PostgreSQL works.
  • Safe upgrade for old laptop databases. When categories became editable, old SQLite files (which stored category names) are converted to the new id format, after first copying the file as a backup, and the row counts are compared before and after backend-spec, commit 46d91f2. That process is called a migration.

What else could have been used

  • Render's free PostgreSQL: rejected, deleted after 30 days goal-spec.
  • Supabase or another hosted PostgreSQL; or SQLite on a paid, permanent Render disk My inference.
  • Keeping data only in the browser (its local storage). No server needed, but the data would exist on one device only, and the backend couldn't enforce the rules My inference.

Gotchas

  • The connection string is a secret, because it contains the database password. It is stored only in Render's settings, never in the code or commits backend-spec.
  • Tests delete tables, so the test setup refuses to run against any PostgreSQL that isn't on the same computer (localhost), and removes any DATABASE_URL from the environment before each test conftest.py.
  • Laptop and online data are separate. Neither is copied to the other goal-spec.
  • Dates are stored as text ("2026-10-07"), and "which month" is found by taking the first 7 characters. It works because this format sorts correctly as text, but the database can't do real date arithmetic on it My inference.
  • Free plan: 0.5 GB and no backups goal-spec.
  • The upgrade to accounts only goes one way. Putting the old backend back would not be enough: it doesn't know about accounts, so it would show every account's categories mixed together. Undoing the deploy means restoring the Neon backup as well as the old code My inference, from reading the old db.py.

Interview questions

Why store money as whole paise rather than as rupees with decimals?Show answer
Whole numbers are exact; decimal numbers in computers often aren't (floating point). If you add many slightly wrong numbers, the total drifts. Storing Rs 12.50 as 1250 paise means every sum is exact, in both databases and on the page. It was a constraint from day one in the goal spec. There's also an upper limit (Rs 10 crore per amount) so totals stay small enough to be exact everywhere, including in the browser.
When "Food" is renamed to "Groceries", why don't the old expenses need updating?Show answer
Expenses don't store the name, they store the category's id (Food is id 1). The name lives in one place, the categories table. Renaming changes that single row, and every expense, in every month, shows the new name the next time it's read, because the backend joins the two tables when it answers. The id also lets the starting six keep their icons after a rename.
How do you make sure running the tests can never wipe the real online database?Show answer
Three layers in conftest.py: (1) every test gets a fresh temporary SQLite file, or a throwaway PostgreSQL given by TEST_DATABASE_URL; (2) any real DATABASE_URL in the environment is removed before each test; (3) if TEST_DATABASE_URL points anywhere other than localhost, the tests refuse to start. In CI, the PostgreSQL is a temporary one that exists only during that run.

GitHub Actions: tests and deploys

What it does

GitHub Actions is GitHub's built-in robot. The file .github/workflows/ci.yml tells it what to do on every push and pull request. This is called CI. It runs four jobs:

  1. Backend tests (SQLite): installs Python 3.14.7 and the packages, runs pytest.
  2. Backend tests (PostgreSQL): the same tests again, against a throwaway PostgreSQL 17 started just for this run (a service container).
  3. Frontend: lint (oxlint), tests (Vitest), then a test build.
  4. Deploy to GitHub Pages: only after all three pass, and only for pushes to main. It builds the page with the Render address and publishes it. This deploys the page only; the backend currently needs a manual deploy on Render.

The three test jobs run side by side; the deploy waits for them (needs:).

Why it's needed

Acceptance criterion 22: the site is "deployed only when every backend and frontend test has passed" goal-spec. A robot runs every test every time, so nobody has to remember to. For the page, the deploy job enforces this. For the backend, it currently relies on a person: the backend needs a manual deploy on Render, which should only be done once CI is green Recorded: build sessions.

Design decisions

  • Backend tests run twice, once per database, because both must follow every rule the same way backend-spec, commit 73d22f8.
  • The throwaway database password is literally "throwaway". The file says it "guards nothing real; the online database is never used here" ci.yml.
  • The Render address is a repository variable, not a secret, because it ends up visible in the page anyway ci.yml, frontend-spec. A first step stops the deploy with a clear message if it's missing ci.yml.
  • Minimal permissions: jobs can only read the code; only the deploy job may write to Pages ci.yml. Giving each job the least power it needs is a common safety habit My inference.
  • Never two deploys at once; a newer one waits for the older to finish ci.yml comment.

What else could have been used

  • Deploying by hand after running tests locally: easy to forget a step My inference.
  • Other CI services (GitLab CI, CircleCI) or letting Render and a static host each build on their own. Actions is built into GitHub, where the code already is My inference.

Gotchas

  • Actions only deploys the page. The backend is deployed by Render, from the same repository. The comment in ci.yml expects Render to deploy automatically after the checks pass, but that never triggered; the backend was updated by a manual deploy Recorded: build sessions.
  • Pull requests are tested but never deployed (if: github.event_name == 'push' && github.ref == 'refs/heads/main') ci.yml.
  • Passing tests isn't the whole check. Criterion 22 also needs a manual check in a browser on the public site goal-spec.
  • This walkthrough page is deployed by the same job, so it only goes live after all the tests pass, like the app My inference.

Interview questions

Why do the backend tests run twice in CI?Show answer
The laptop uses SQLite and the online app uses PostgreSQL. They behave differently in small ways: how new ids come back, how sums are typed, how capital letters are compared. The spec requires both to follow the same rules, so the same tests run against each. Differences like sums needing a cast to whole numbers only show up on PostgreSQL, so running both is what catches them.
What stops a broken change from reaching the live site?Show answer
The deploy job has needs: [backend-sqlite, backend-postgres, frontend], so it only starts if all three test jobs succeed, and only for pushes to main. If any test, the lint check or the build fails, the old page stays live. This was tested on purpose: a deliberately broken negative-amount rule was pushed on a throwaway branch, and both backend jobs went red. For the backend, the honest answer is "a person": Render's auto-deploy didn't trigger, so the backend is updated by a manual deploy, which should only be done once CI is green. Tests can only catch what they test, so there's also a manual browser check.
Where are the app's secrets kept, and why isn't the backend address one of them?Show answer
The real secret is DATABASE_URL, which contains the database password. It lives only in Render's settings and never appears in code, commits or CI. The backend address (VITE_API_BASE) is built into the page, and anyone can read the page's code in their browser, so treating it as a secret would protect nothing. It's stored as a plain repository variable.

Journey 1: adding an expense

You're logged in, and you add "Lunch, Rs 12.50, Food, today" on the live site. Here is everything that happens, in order. Open "Under the hood" for the file and function involved.

BrowserRenderNeon: these labels show where each step happens.

  1. BrowserYou click "+ Add expense". The Add expense popup (a modal) opens on top of the page, with the cursor in Amount, the date set to today, and Category showing "Choose a category".
    Under the hood
    App.jsx sets adding to true, which shows AddExpenseModal.jsx; it calls the browser's showModal(). Today's date comes from dates.js, in IST. Nothing has been sent to the backend yet.
  2. BrowserYou fill it in and click "Add expense". The page runs its convenience checks first. If the amount were empty, 0 or had 3 decimals, a message would appear under that box and nothing would be sent.
    Under the hood
    checkForm() in expenseForm.js. parseRupees("12.50") in money.js gives 1250. The button changes to "Saving..." and is disabled, so you can't send it twice.
  3. BrowserThe page sends a request. It's a POST to https://…onrender.com/api/expenses with this JSON body:
    {"amount_paise": 1250, "category": "Food", "date": "2026-10-16", "note": "Lunch"}
    Under the hood
    request() in api.js uses the browser's fetch, adds the Content-Type: application/json label and your token in the Authorization header, and sets a 90-second timeout. The address came from VITE_API_BASE when the page was built.
  4. BrowserRenderThe browser asks permission first (CORS). The page (from github.io) is talking to a different origin (onrender.com), and it is sending JSON, so the browser first sends a small preflight request asking "may this page send this?". The backend says yes because https://shivanisujith.github.io is in ALLOWED_ORIGINS.
    Under the hood
    CORSMiddleware in main.py allows the methods GET, POST, PUT, DELETE and the Content-Type and Authorization headers. The browser does the preflight on its own; the app's code never sees it.
  5. RenderIf the server was asleep, it wakes up first (about a minute). When it starts it runs init_db(), which sees the tables already exist and changes nothing.
    Under the hood
    lifespan() in main.py runs at start-up and calls db.init_db() → _init_postgres(). If the wait goes past 5 seconds, the page shows "Waking up the server…" (Journey 2).
  6. RenderNeonThe backend checks every rule again. First it checks your token: no valid session means a 401 and nothing else happens (Journey 3). Then it loads your current category names from the database, then checks in a fixed order: amount (a whole number, more than 0, at most Rs 10 crore), category (exactly a current name), date (a real date, not after today in IST), note (100 characters at most, after trimming spaces).
    Under the hood
    add_expense() in main.py calls validate_expense() in validation.py. The first failure raises an ApiError, sent back as a 422 with the error object, and nothing is saved.
  7. RenderNeonThe expense is saved. One SQL INSERT inside a transaction; the database gives the new row an id and checks its own safety rules too.
    Under the hood
    INSERT INTO expenses … RETURNING id. created_at is set to the current time (UTC), used only to order expenses on the same date. Then fetch_expense() reads it back joined with its category name.
  8. RenderBrowserThe backend answers "201 Created" with the saved expense, including its new id and category_id.
  9. BrowserThe popup closes and a success message shows. "✓ Expense added" appears in the Expenses box for about 3 seconds, and the cursor goes back to "+ Add expense".
    Under the hood
    handleAddSaved() → succeeded() in App.jsx; the message comes from useSuccessMessage() in successMessage.js.
  10. BrowserRenderNeonThe page asks for everything again. It doesn't add 12.50 to the total itself. It sends four requests at once: the expense list (for the month you're viewing), the summary (cards and this month's total), the list of months, and the total for the month shown in the Spent box.
    Under the hood
    loadAll() in App.jsx uses Promise.all / Promise.allSettled so the four run together. The backend's get_summary() adds up each category with SQL SUM and sets over_limit only when spent is strictly more than the limit.
  11. BrowserThe screen updates. The new row appears ("Lunch", "Food · Today", Rs 12.50), the Food card's spent and progress bar move, and the total and insight line change. If Food is now over its limit, the card turns red with "Over limit by Rs X", but the expense is still saved: going over a limit never blocks saving goal-spec.

Journey 2: when the server can't be reached

The backend is stopped, asleep, or the network is down. The rule: the page must never be blank or broken, and must say clearly what's wrong goal-spec, criterion 8.

Scenario A: you open the page and the backend doesn't answer

  1. GitHub PagesThe page itself still loads. It comes from GitHub Pages, which is separate from Render, so the title, today's date (from your computer's clock) and the "+ Add expense" button all appear.
  2. BrowserThe page sends its four first requests and starts a 5-second timer.
    Under the hood
    The useEffect in App.jsx starts loadAll() and a setTimeout of 5000 ms.
  3. BrowserAfter 5 seconds with no answer, a calm note appears under the subtitle: "Waking up the server, this can take up to a minute…". It's muted plum, not red, "because nothing has gone wrong" frontend-spec. Screen readers announce it politely.
  4. BrowserEither the server wakes up (the note disappears, data appears, done), or the request fails. A stopped server usually fails at once ("connection failed"). A server that never answers is given up on after 90 seconds.
    Under the hood
    In api.js, any error thrown by fetch (connection refused, no network, or the 90-second AbortSignal.timeout) becomes ApiError('unreachable'). A real answer with a 4xx/5xx status becomes a different kind (invalid, not_found, server).
  5. BrowserA red banner appears just under the title, with a Try again button:
    Can't reach the server. Check that the backend is running, then try again.
    The Spent box shows Rs – (never "NaN"), and anything already loaded stays on screen.
    Under the hood
    loadAll() collects the four results; if any is 'unreachable', it sets unreachable to true and ServerBanner.jsx shows with role="alert", so screen readers announce it straight away.
  6. BrowserYou click Try again. All four requests are sent again. The banner goes away only if none of them is unreachable.

Scenario B: the server goes away while you're adding an expense

  1. BrowserYou click "Add expense" in the popup, and the request fails.
  2. BrowserThe popup stays open with everything you typed, shows the "Can't reach the server…" message at its top, and the red banner appears on the page behind it. You can press Add expense again when the server is back.
    Under the hood
    The catch in handleSubmit() of AddExpenseModal.jsx checks error.kind === 'unreachable', sets the top message and calls onUnreachable(). Nothing was saved, so trying again won't create a duplicate.

Why it's built this way

  • 90 seconds, not 10. The wait was originally 10 seconds. When the app went online it was raised to 90 "because the online backend runs on a free plan that sleeps… and takes about a minute to wake up" api-contract-spec, commit 738f4a2. With 10 seconds, every first visit after a quiet spell would have shown an error.
  • Three different messages for three different problems: "can't reach" (no answer at all), "something went wrong on the server" (a 500 answer), and the rule message (a 422). That's why 500 answers must carry CORS headers (see Render's interview questions).
  • How it's tested: automated tests fake an unreachable server (wakingNote.test.jsx, App.test.jsx). Criterion 8 is also checked by hand: on the laptop by stopping the backend with Ctrl+C, and online by clicking Suspend on the Render service, then Resume frontend-spec, section 6.

Gotcha: a CORS refusal also makes fetch fail without an answer, so a wrong ALLOWED_ORIGINS setting on Render would show up as "Can't reach the server" even though the server is running My inference, from api.js.

Journey 3: signing up and logging in

You open the live site for the first time and create an account. Here is what happens, and how the backend knows it's you on every request after that.

  1. BrowserThe log in screen shows. There's no saved token, so the page shows a cream box with Username and Password instead of the dashboard frontend-spec.
  2. BrowserYou click "New here? Create an account". The heading changes, and a warning appears: "This is a demo. Don't use a password you use anywhere else." The page checks the rules first (username 3 to 20 letters, numbers or underscores; password 8 to 64 characters, not the same as the username) and sends nothing if one fails frontend-spec.
    Under the hood
    LoginScreen.jsx switches mode to 'signup'; checkLoginForm() in loginForm.js runs the checks.
  3. BrowserRenderThe page sends POST /api/auth/signup with your username and password, over HTTPS so nobody in between can read it. This is one of only two requests that need no token.
  4. RenderNeonThe backend checks the rules again, lowercases the username (so "Shivani" and "shivani" are the same account), and refuses a taken one with "That username is already taken." backend-spec, rules A1 to A6.
  5. RenderNeonThe account is created, in one all-or-nothing step backend-spec, rule A7:
    • the password is turned into an Argon2 hash, and only the hash is saved;
    • the account gets its categories: the old unclaimed data if there is any (only the very first account after the upgrade), otherwise the six starting ones;
    • a session starts: a random token (32 random bytes) is made, and only its SHA-256 fingerprint is saved, with an end time exactly 7 days later.
    Under the hood
    sign_up() in main.py; hash_password() and start_session() in accounts.py. The claim is UPDATE categories SET user_id = ? WHERE user_id IS NULL.
  6. RenderBrowserThe backend answers "201 Created" with the token. The page saves it in localStorage and opens the dashboard: "Hi shivani, here's your spending" frontend-spec.
  7. BrowserRenderEvery request after that carries the token in a header: Authorization: Bearer <token>. The backend fingerprints it, finds the session, and so knows whose data to use api-contract-spec.
    Under the hood
    logged_in_user() in accounts.py runs before any other check (rule S5), so a request without a valid session never learns or changes anything.
  8. RenderBrowserWhen the session ends, you're sent back to the log in screen. No token or an unknown one gives a 401 with "Please log in to continue."; after 7 days it's "Your session has expired. Please log in again." Using the app doesn't extend the 7 days goal-spec, criteria 30 and 31.
  9. BrowserRenderLogging out asks the backend to delete the session, then removes the token and clears the dashboard, even if the server can't be reached. The old token can't be used again frontend-spec, goal-spec criterion 29.

Why it's built this way

  • One message for a wrong username and a wrong password: "Username or password is incorrect.", "so it doesn't reveal which usernames exist" goal-spec, criterion 28.
  • Hashes, not passwords; fingerprints, not tokens. Someone who got a copy of the database still couldn't read a password or log in as anyone backend-spec.
  • The old data goes to the first sign-up. The online app had data before accounts existed, and it had to belong to someone. The first account to sign up after the upgrade takes all of it; everyone after that starts with six empty categories goal-spec.

How this was built

From the four spec files and the git history between 7 and 16 October 2026.

Spec-driven development

Before any code, the goal was written down as a spec (goal-spec.md, the first commit), then three more detailed specs for the frontend, the backend and the API contract. The goal spec wins any disagreement. It lists 34 acceptance criteria (24 to 34 were added for login), each saying how it is decided: "automated test", "manual browser check", or "CI run" goal-spec.

CLAUDE.md, the instructions for the coding agent, says: read every spec before changing code, stop and report any conflict instead of guessing, never edit specs unless asked, and treat the "Out of Scope" list as binding CLAUDE.md.

The history shows the habit: 19 of the first 51 commits change a spec, and new features usually start with a spec-only commit followed by the code. For example, "Add month arrows and month filter to specs" (2393e15) then "Add month arrows to the Spent box…" (934f5be).

Tests written first

In almost every phase, the new tests were written first and run against the old code, where they failed, as they should, because the feature didn't exist yet. Then the change was made, and they passed Recorded: build sessions. A test that has been seen failing proves it can actually catch the problem.

Git can't show this order, because each test and the code it tests were committed together once the phase was approved. The order is known from the build sessions, not from the history.

Test counts from the last local run, before the login deploy Recorded: build sessions:

  • 449 backend tests on SQLite, plus 8 skipped: the online-database upgrade tests, which only apply to PostgreSQL (test_postgres_login_upgrade.py)
  • 438 backend tests on PostgreSQL (a throwaway one in Docker), plus 19 skipped: the laptop file upgrade tests, which only apply to SQLite (test_migration.py, test_login_migration.py)
  • 290 frontend tests

Test names read like spec sentences, for example test_a_limit_above_the_maximum_is_refused_and_the_old_limit_kept.

Deliberate rule-breaks: breaking the app on purpose

Passing tests only mean something if the tests would fail when the app is wrong. So rules were broken on purpose to prove the tests notice, and then put back Recorded: build sessions:

  • Phase 6, the final check of the whole app against all 23 acceptance criteria: the negative-amount rule was deliberately broken, so a negative amount would be accepted, and the over-limit rule was changed from "more than the limit" to "at least the limit". The tests caught both, and both rules were restored.
  • Checking that CI catches it too: a broken negative-amount rule was pushed on a throwaway branch. Both backend jobs (SQLite and PostgreSQL) went red, proving a broken rule can't slip through to a deploy.
  • Many other phases had their own break-and-restore checks.

This is a simple form of what's sometimes called mutation testing.

Exceptions written into the rules

The specs also set strict rules and then make a few exceptions on purpose, writing down why:

  • "No charts", except a progress bar on each category card goal-spec, Out of Scope.
  • "Sage is the only accent colour", except the icon circles, which use three soft tints taken from the existing palette. Icons are never red, so red always means "over limit" or "error" frontend-spec.
  • Accounts on free plans: "Login here is a demo and stays on the free plans"; the app would move to paid plans only for real personal data or more traffic goal-spec, Technology.
  • The over-limit card's light red is "deliberately stronger than a pale pink" so it stands out from the creams, not only through its border frontend-spec.
  • Python's usual type check is avoided on purpose: type(value) is not int instead of isinstance, because in Python True and False count as numbers, so {"amount_paise": true} would otherwise sneak through as 1 paisa validation.py comment.
  • Tests sometimes bypass the API on purpose: insert_expense_row() writes straight into the database "skipping the API's checks", for example to store a future date that the API would refuse conftest.py.
  • A fake popup for tests: the test browser (jsdom) has no popup support, so dialogStub.js adds the two methods the app uses dialogStub.js.

Known limitations

Each one is labelled with where it comes from: the goal spec, the build sessions, or my own reading of the code.

Accounts are a demo goal-spec

Anyone with the link can create an account. Don't reuse a password used anywhere else, and don't enter real personal spending online.

Login is for learning only goal-spec

Nothing stops someone from guessing passwords many times. The token is kept in browser storage that a harmful script on the page could read, shared by every page under shivanisujith.github.io. A forgotten password can't be recovered. The online data from before accounts went to whoever signed up first after the upgrade.

The free server sleeps goal-spec

After 15 minutes with no visitors, the first visit takes about a minute.

Laptop and online data are separate goal-spec

Nothing is copied between the two.

No backups goal-spec

The free plans have no backups set up. If the online data were deleted, it would be gone.

Free-plan size limit goal-spec

The online database holds at most 0.5 GB.

Backend deploys are manual Recorded: build sessions

Render's auto-deploy didn't trigger, so backend changes only go live after someone deploys them by hand in Render. GitHub Actions only deploys the page, so the page and backend can briefly be out of step.

No protection against abuse My inference

Nothing limits how many requests someone can send (no rate limiting), so a script could create endless accounts or keep guessing passwords.

Rare clashes between simultaneous users My inference

Some checks and the change that follows are separate steps. Two people acting at the same instant could, in theory, get past a check like "at most 20 categories". The database's own rules still catch duplicate names and missing categories, but that would show as a "server error" rather than a friendly message.

One limit for every month backend-spec

A limit can't differ from month to month, and can be changed but not removed (except by deleting its category).

Fixed to India goal-spec

Rupees only, and "today" is always India time, wherever you are.

No alerts if something breaks My inference

Errors are written to Render's logs, but nothing tells anyone. Problems are only noticed when someone uses the app.

Needs the internet My inference

The page can't save anything while offline; it shows the banner and keeps what you typed until the server is back.

Glossary

Every dotted word on this page, in one place.

Acceptance criterion
One checkable statement that must be true for the work to count as done, e.g. "an amount of 0 is refused".
API
Application Programming Interface: the agreed list of requests the backend understands and what it answers. Here it is written down in specs/api-contract-spec.md.
Automated test
A small program that uses your app and checks it behaves as expected, e.g. "adding 0 rupees is refused". Run in seconds, again and again.
Backend
A program running on a server that the page talks to. It checks rules, saves data and works out totals. Here: the FastAPI program on Render.
Backup
A copy of data kept somewhere safe, so it can be restored if the original is lost.
Browser
The app you use to visit websites: Chrome, Safari, Firefox, Edge.
Build
Turning the source code you write into the final files a browser downloads.
CHECK rule
A rule written into a table itself, e.g. amount_paise > 0. The database refuses any row that breaks it.
CI (continuous integration)
Automatically running all the tests on every change, so problems are caught before they go live.
Connection string
The full address of a database, including the username and password needed to get in.
CORS
Cross-Origin Resource Sharing: a browser rule. A page from one address (origin) can only read answers from a backend at another address if that backend says the page is allowed. It protects browser users, not the backend.
Database
Organised storage that keeps data safe between visits and restarts, a bit like a set of spreadsheets that programs read and write.
Deploy
Putting a new version live, so real visitors get it.
Endpoint
One address in the API that does one job, like /api/expenses (list or add expenses).
Environment variable
A named setting given to a program when it starts, like DATABASE_URL. Secrets are kept there, never in the code.
FastAPI
A Python library for building backends. You write a function per endpoint; it handles reading requests and sending responses.
fetch
The browser’s built-in function for sending a request from JavaScript and waiting for the response.
Floating point
How computers usually store decimal numbers: fast, but approximate. In JavaScript 0.1 + 0.2 gives 0.30000000000000004.
Frontend
The part of an app you see and click. It runs inside your browser. Here: the React page.
GitHub Actions
GitHub’s built-in robot: it runs scripts, like tests and deploys, on GitHub’s computers whenever you push.
GitHub Pages
GitHub’s free hosting for static websites.
IST
India Standard Time, 5½ hours ahead of UTC.
JavaScript
The programming language that browsers run. It makes pages interactive.
jsdom
A pretend browser that runs inside the test program, so page tests don’t need a real browser.
localStorage
A small storage area the browser keeps for each website, which survives reloading the page. The login token is kept there.
JSON
A simple text format for data, made of names and values: {"amount_paise": 1250, "category": "Food"}.
Lint
A tool that reads code without running it and flags likely mistakes. Here: oxlint.
Migration
A one-time step that converts an older database to a newer format, keeping all its data.
Modal (popup)
A box that opens on top of the page and must be closed before the rest of the page can be used again.
Mutation testing
Deliberately putting a small bug into working code to check that the tests catch it. If the tests still pass, they aren’t really testing that rule.
Neon
A company that hosts PostgreSQL databases online.
Origin
The "home address" of a web page: its scheme and domain, e.g. https://shivanisujith.github.io.
Paise
1 rupee = 100 paise. Storing Rs 12.50 as 1250 paise keeps money in whole numbers, which computers handle exactly.
Password hash
A scrambled, one-way fingerprint of a password. The backend can check a typed password against it, but nobody can turn it back into the password. Made here with Argon2.
PostgreSQL
A widely used database that runs as its own server program. Used online, hosted by Neon.
Preflight
A small permission-check request (method OPTIONS) the browser sends on its own, before certain cross-origin requests such as ones carrying JSON.
Push
Uploading your saved changes (commits) from your laptop to GitHub.
pytest
The tool that runs the backend’s Python tests.
Python
A programming language, popular for backends and data work. The backend is written in it.
React
A popular JavaScript library for building pages out of reusable pieces called components (the popup, the card, the banner…).
Reference (foreign key)
A database rule that a value must point at a row that really exists, e.g. an expense’s category_id must be a real category.
Render
A company that runs your programs on its servers. Its free plan sleeps when nobody uses it.
Repository (repo)
A project folder tracked by git, with the full history of every change. This one lives on GitHub.
Request
A message the browser sends to a server asking for something, such as "give me the expenses" or "save this one".
Response
The server’s reply to a request: a status code (did it work?) and usually some data.
Server
A computer that stays switched on and connected to the internet, waiting to answer requests.
Service container
A throwaway mini computer started just for one CI run, here running PostgreSQL, and deleted afterwards.
Session
One "logged-in" period. It starts when you log in or sign up and ends when you log out or after 7 days.
Spec (specification)
A written description of exactly what the software must do, agreed before the code is written.
SQL
The language used to talk to a database, e.g. SELECT * FROM expenses WHERE date = ‘2026-10-16’.
SQLite
A database that is just a single file, with no separate server. Used on the laptop and in tests.
Static site
A website whose files are the same for every visitor. The host just hands the files out; it runs no code of its own.
Status code
A number in every response saying how it went: 200 OK, 201 Created, 204 done (nothing to send back), 401 not logged in, 404 not found, 422 your input broke a rule, 500 the server broke.
Table
Like one sheet in a spreadsheet: rows of records, each with the same columns.
Timeout
A maximum wait. If no answer arrives in time, the request is given up on.
Token
A long random pass the backend gives the browser when you log in. The browser shows it with every request to prove who it is, like a wristband at an event.
Transaction
A group of database changes that happen all together or not at all, so a failure halfway leaves nothing half-done.
Unique index
A lookup structure that makes searching fast. A unique one also forbids duplicates, here duplicate category names within one account (ignoring capitals).
UTC
Coordinated Universal Time: the world’s reference clock. Servers usually run on it.
Validation
Checking input against the rules before accepting it, e.g. "amount must be more than 0".
Vite
A tool for building web pages. While developing, it serves the page on your laptop; for publishing, it bundles all the code files into a few small, fast ones.
Vitest
The tool that runs the frontend’s JavaScript tests.
WCAG AA
Web Content Accessibility Guidelines, level AA: a widely used standard. Among other things, text must contrast with its background by at least 4.5 : 1, so it’s readable.
